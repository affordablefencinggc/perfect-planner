# Plan approval connection — implementation contract

Status: in progress, not publication or release evidence.

## One ledger, one compact map

`TaskDraftLedger` remains the editor and complete record of obligations. `TaskDraftMap` remains its summary. Do not create a second task model or replace details with generated summaries. Existing strict LOCAL_DRAFT history remains unchanged, including archived tasks and inventory bindings.

UI253 implementation (verified in scope on DANS1:351 Node,162 UI and258 browser steps across identical-source campaigns): ProjectProvider holds only an ephemeral checked planning observation. The observer compares the complete saved Ledger before and after current approval readback, checks all three parent heads and exact project/root/census, and refuses dirty forms or pending recovery. Home and the compact map consume that same observation; Ledger must also pass the shared check before displaying current approval. Notifications from committed draft/recovery changes are invalidation hints, not receipts. They remove checked status immediately; an explicit Check reads the pending/current state. Focus, changed parents, project switches and late responses cannot promote a cached approval. Registered Plan authority and native execution permission remain separate; no authority store is created or promoted by these UI checks. Synthetic workflow proof is not native execution or full-release acceptance.

## Review packet

A separate versioned, bounded PLAN_REVIEW_PROPOSAL retains the entire validated ledger and component catalog, their content digests, exact architecture/folder/component head revisions and digests, and explicit task-to-component associations. Every active task and every component must be accounted for. Unresolved draft findings, unknown associations, uncovered file claims, stale parents and incompatible access are blockers. Associations do not silently rewrite existing component task labels. Review packet creation alone grants neither approval nor execution.

Content hashes demonstrate content consistency, not authenticated authorship, live parent freshness, filesystem ownership or tamper-proof custody. Publication must independently inspect current host records.

Generic component dependencies do not justify inventing an all-to-all execution sequence. The review packet exposes declared task ancestry and unresolved inter-task or within-task ordering separately. An internally consistent packet can still contain ordering questions: its integrity verifier is not an approval-readiness verdict. The eventual publication gate must require explicit resolution and preserve the reviewed decision. Every component file claim must have compatible task coverage as well as every task claim remaining inside its associated components; checking only one direction can silently omit work.

## Host custody before publication

The existing development authority root is selected by host composition. New paths must derive from validated project identifiers beneath that root, never request-supplied filesystem paths. Retain browser-declared project/root/census bindings explicitly as declarations; the host cannot inspect browser directory handles. Compare imported project ID derivation to its root digest. Preserve changed bindings and require explicit reconciliation; never overwrite another project's history.

Native verified registration remains a separate source. Do not provide a native registration callback that merely echoes browser input. The existing native proposal protocol and execution grants must keep their current boundaries.

Original idempotent retries compare their original predecessor and return both historical submitted head and actually observed current head. Absent inspection creates no project record; explicit submit creates only the derived project directory and uses the existing proposal journal. Existing records and failure bytes are retained. Same-origin/session checks are transport capabilities, not person authentication or live folder verification. New approval publication remains unimplemented at this checkpoint.

Reuse the full-ledger proposal store with a host-selected journal and binding. Acquire cooperating locks in architecture → folder → component → proposal → planning approval order; never acquire these recursively or invert the existing order. Exact current heads and retained ledger digest/revision must still match at publication. Preserve uncertain appends and make retry idempotent; a returned toast is not proof of storage.

### Required rejected-request follow-through

A stale-parent refusal must not strand a pending original forever. Add an explicit withdrawal of an unpublished request, not a silent discard. Under the existing approval-journal lock, the host must either find the exact published original and reflush/read back its real publication receipt, or retain a bounded, durable full-original withdrawal record. Both publication lookup points must check withdrawals under that same lock so a delayed parallel request cannot publish after withdrawal. Merely inspecting an absent approval or receiving a generic error does not prove there is no in-flight publication.

Keep withdrawal outcomes separate from approvals: no approval, execution, or native authority is granted. Local recovery may move the original to retained terminal history only after checking that receipt. Prove publish/withdraw races, delayed publication, exact retry after a lost response, changed-request conflicts, corrupted/partial/full storage, cross-tab completion and fresh review after withdrawal. This remains unimplemented at UI248; happy-path approval/reload and original retry evidence do not close it.

## Required proof

### Next implementation: one approval record, not another ledger

Retain the existing review packet unchanged in a bounded approval record downstream of `withCurrentPlanningReview`. Bind its digest, retained proposal head, original request, expected approval head and explicitly declared actor/source. Reuse the safe append/CAS/idempotency/flush/readback patterns of the existing task-check store, not its native registration claims or incompatible task-check schema. The generic journal helper is not an authority store: its read bounds, path safety and transaction semantics are insufficient for this purpose.

An exact retry must recover the original stored result without appending. Reusing the request ID with changed content must refuse. A new approval requires current parent/proposal locks and the expected approval head. An original retry after a successor or parent change must return historical evidence explicitly, never silently relabel it current. Keep historical lookup separate from current-parent composition to avoid inverted lock acquisition. Missing, corrupt and unavailable storage must not erase earlier evidence or produce an approval-success state.

Existing confirmation subjects do not currently accept this review packet. Do not put a Plan approval into an unrelated task subject or manufacture native gesture proof for a browser confirmation. Local-development confirmation and native trusted approval must remain distinguishable; neither this record nor its UI permits execution.

UI247 implementation retains `PLAN_APPROVAL_RECORD` with the complete packet, exact retained proposal head, original request, digest-bound approve decision and fixed host actor/source. `inspect` returns historical records with current parents unchecked. `inspectCurrent` first captures the requested approval head under its journal lock, releases it, then checks current parents/proposal and rechecks the exact approval head/record under the downstream lock. New publication uses the same current-parent boundary; exact retries reflush/read back the original record with current parents explicitly unchecked. A changed request under the same ID refuses.

The protected local-development planning middleware exposes `approval-inspect`, `approval-publish` and `approval-current` under its existing same-origin transport capability. All routes reject caller paths and actor/source overrides.
