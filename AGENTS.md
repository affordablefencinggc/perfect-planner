# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Perfect Planner design contract

- Agent onboarding (2026-09-14): primary entry is a right-hand Connect your agent drawer, without navigation or new tabs. The first journey is one plan, not an app tour. Target one-paste setup with explicit native consent, verified project/plan identity and shared browser/Tauri authority. A diagnostic prompt is not one-paste setup; existing project-level permissions are not plan-level isolation. Never describe either as completed until the native/public-helper journey is proven.

- Live walkthrough priority (2026-09-14): one installed journey takes precedence over unrelated component work: connect an IDE agent, submit a small plan, see its nodes, run one approved change and inspect its result. User wants to watch this live. Developer Notes must separately summarize each exchanged prompt/reply, observable actions, errors, suspected cause, proposed solution and verification evidence. Summaries are not private reasoning or proof; missing exchange capture must be explicit. Do not claim MCP tools automatically expose full IDE conversations. Reuse the existing browser tab; never open repeated evidence tabs.

- Agent interaction (user clarification, 2026-09-14): agents may use browser tools or Fast CDP to interact with Planner's actual UI. Show attributable, observed interaction, not decorative cursor activity presented as proof. MCP pairing or submitted-plan reading alone must not be labelled browser-control access. Keep DANS1-only testing and separate project-scoped permissions; this is not blanket desktop, credential or deployment authorization.

- Change accounting (2026-09-06): every numbered change must remain accounted for. Show failures and unresolved outcomes immediately with the affected task, observed failure, known cause or explicit unknown, owner and next action. Commits and diagnostic messages are not verification receipts. Never subtract passing checks from commits to infer failed changes; use the same revision-bound task population. Preserve history and distinguish archived work from completed work.

- Desktop-control scope (user update, 2026-09-05): Computer Use or Desktop Commander is allowed on the remote testing PC DANS1 only. Never activate windows, click the desktop or capture desktop screenshots on this development PC. Prefer MCP/direct app APIs for routine work. Before remote desktop actions, verify the selected device is DANS1; never accept an implicit first-online/default device. User authentication, credentials and security protections remain out of scope. If no verified DANS1 desktop connection exists, continue SSH/headless verification and request remote-device connection rather than controlling this PC.
- Run heavy builds and tests on the user's DANS1 testing PC over SSH alias `tonys-test-pc` (2026-09-05), not this PC. Require batch authentication and strict host-key checking. Use a fresh task-specific folder and preserve existing work. Return logs and headless-browser screenshot evidence, clearly distinguishing web proof from native desktop verification. Never copy private keys, inspect saved credentials, disable security protections, or make payments. Verify a standalone Codex CLI works over SSH before any remote Codex task; do not bypass the desktop-bundled CLI's access restrictions.
- Worker coordination is a core requirement: finalized planning produces revision-bound compact worker briefs derived from the authoritative ledger; summaries never replace obligations or evidence. Tool access must be mediated by an authority-owned broker, with scoped grants and enforced transitions, not merely prompt instructions. Durable message acknowledgments, independent worker/progress monitoring and AFK notifications must not rely on an LLM remembering to communicate. Never equate heartbeat with progress, acknowledgment with understanding, or push-service acceptance with the user seeing an alert.

- Beginner-friendly clarity is a core feature (2026-09-05): default to a clean Simple view with readable text, stable navigation, plain-language outcomes and the next useful action. Offer an opt-in Advanced view for exact diffs, refs, worktrees, checks, hooks, policies and diagnostics. Both views share the same project identity, state machine and safety rules; changing view never mutates work or disables protections. Experts can use the simple view too. Preserve familiar editor/CLI interoperability without requiring command-line knowledge or exposing technical mechanics everywhere.
- Simplify decisions, not truth: always show what will change, what is blocked, and how to preserve/recover work. Do not hide failures, use fake progress, label configuration as success, or silently send code to third parties. Research hypotheses must be validated with beginners and experienced developers, not treated as proven from forum anecdotes.

- Product priority (2026-09-05): Perfect Planner is a safe multi-worker app-building coordinator, not merely a Git dashboard. Put branch/worktree integration, preservation of unfinished work, exact-candidate CI, and recoverable merge transactions at the centre. Users work with named change packages and clear actions; Git remains an optional compatibility adapter, not the user-facing workflow or sole source of task/evidence truth.
- Never promise bulletproof or no-code-loss guarantees without crash, concurrency, disk/error, dirty-worktree, stale-base and recovery evidence. Do not automatically discard, reset, force-remove, prune or rewrite user work. Preserve rejected candidates and explain recovery before cleanup. Configuration, adapter health, local checks, merged-candidate CI and production deployment are separate facts.
- Rehearsal retains its candidate working copy; it must not automatically abort or remove it after a check. A content snapshot is not an exclusive filesystem lease, and ordinary Git/worktree locks do not prevent another process editing files. Keep local verification separate from permission to promote or delete. Retention needs visible ownership, disk usage and a later preserve-first disposition workflow; it is not a claim that cleanup is solved.

- The primary journey is Project Home followed by five numbered stages: Define, Coordinate, Build, Prove, and Release. Do not restore a flat row of every workspace.
- A selected stage reveals only its contextual subpages. Project Home must show current stage, honest completion, active responsibility, unresolved collisions, the exact next action, and why it is blocked.
- The searchable Index is a separate overlay/drawer available everywhere; it is not a sequential build stage.
- Build is a dedicated workspace with the guarded conveyor. Plan, Collisions, Allocation, Build, Integrity, Evidence, and Release/Ledger remain separate surfaces.
- Every workspace carries a compact “you are here” context: purpose, required outcome, and what unlocks the next stage.
- Keep Plan, Allocation, and Evidence as separate full workspaces; never cram them into one dashboard.
- The left repository rail and right inspector are concealed edge drawers by default.
- The shared bottom operations dock is collapsed by default and contains logs, branches/worktrees, CI/review, and the merge queue—not evidence.
- The Operations console is an anchored bottom sheet: drag its header vertically to resize it, double-click the header to collapse it, and keep selectable/copyable project-scoped events plus distinct local, catcher, proof, CI-queue, and production states. A configured tool is never displayed as an executed or passing receipt.
- Evidence is a dedicated wide, Figma-like spine canvas with screenshot-led branches.
- Preserve the established warm beige, white, chromium-silver, charcoal, monospaced, softly bevelled ledger visual language.
- Green is only a verified-success signal; amber is risk; red is a hard stop.
- Branch and worktree allocation follows a deterministic conveyor with visible ownership, claims, proof, review, CI, and merge state.
- All implementation is clean-room. Do not copy source code, package configuration, executable assets, or Git history from the original Perfect Planner repositories.
- The small orange planner worker completes one slow lap around its assigned card, drawing a green success trail behind it; one full return to its starting point marks the package finished and the worker stops.
- The head orchestrator is the same orange planner character at a larger scale, perched directly on top of P1. It has no permanent dashboard or feed; updates stay hidden until the character is clicked.
- Plan cards, phase capsules, and whole-plan map pieces use unmistakable chromium bezels: a thick dark metal inner edge, pale silver outer casing, rounded corners, and a soft cast shadow. Blue never replaces the bezel; it only outlines the current selection.
- The Plan workspace includes a hidden Quick brief for zero-lag model handoff. It summarizes the goal, exact current package, owner, claims, collision order, next action, blockers, and proof rule without replacing the full ledger.
- Do not claim UI or workflow completion from builds, component tests, or static screenshots alone. Audit the running app end to end with a real repository wherever the runtime permits it, and clearly label native-only or unavailable paths before the user reaches a dead end.
- The Perfect Planner mind map is the compact, easy-to-scan summary of the work. The Ledger owns the complete task, dependency, conflict, owner, and evidence detail; never overload the map with ledger-level detail.
- "Finished" means the app survives real-life use: clean install, very large repositories, interrupted or failed indexing, reload and browser history, multiple isolated projects, stale or revoked folder access, offline/error states, corrupted persisted metadata, and recovery without presenting sample or last-known data as live truth.

- Creation workspace (user request, 2026-09-27): provide a Creation section within the Build stage where users can see workers busy at their own workstations during real work. Show each worker's assigned task, latest observed action, timestamps, blockers and attributable output or preview when available. Animate work only from fresh observed activity; distinguish working, waiting, blocked, disconnected/stale and finished. Heartbeats, agent-reported progress and verified results remain distinct. Missing visibility must be explicit; never simulate live worker actions or expose private reasoning, credentials or unrelated desktop content. Keep the existing ledger authoritative and link workstation activity to project, task and attempt history.

- Goal-first route planning (user request, 2026-09-27): never make a missing-input report the end of the journey. Keep the user's goal and current task visible; propose ordered alternative paths to obtain inputs or achieve the outcome, with concrete next actions, explained ranking and fallback branches. Use Sonar-assisted evidence where available, label assumptions and research availability, and draw a clickable task/path mind map. Complete independent planning before presenting scoped connector/import actions for user authorization. A connection action must resolve to a verified supported connector or an explicit alternative, never a fake connected state. Feed selected tasks into Creation workstations and retain decision/history in the authoritative ledger.

- Build chat and orchestration (user direction, 2026-09-27): Build defaults to one main conversational workspace with an optional resizable split for output, preview, files or model conversations, matching the interaction pattern in the user's references. Multi-model panes are optional. A shared composer targets one selected model or an explicitly selected group. Peer review, including Jev as a selectable reviewer when configured, is an additional tool in the same chat/build flow. Preserve original outputs, rounds, revisions, disagreements, decisions, errors and costs. Display actual activity and provider availability; never invent model replies or claim consensus/independence from duplicated model identities. Scope, budget, cancellation and execution authority remain explicit. The chat and split layout must retain drafts/history when switching views. These latest directions supersede a conveyor-only Build presentation; the guarded execution pipeline remains beneath the conversational experience.
